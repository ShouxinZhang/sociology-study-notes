# 仓库 Agent 指令

> 本文件是仓库根目录 `AGENTS.md` 的中文翻译版本。若两者内容不一致，以根目录原文件为准。

- 任何时候都必须将模块化，层次化思想应用起来。善于利用 tree 或者 graph 结构。主干文件绝对不能臃肿，能拆分到子模块的就到子模块里。例如书写 SKILL 时，尽可能将模板等冗长细节放到 `references` 或者 `scripts` 子文件夹里；又比如软件模块，不管是 Python、TypeScript 之类，都应该时刻注意，不要把太多功能堆放在单个文件里，而是拆分为有层次的多子文件夹结构。
- 在构建新代码之前，先审查现有代码，以减少冗余。
- 任何新变更都应尽可能简单。不要增加额外分支，也不要擅自规划未经授权的功能。
- 在任何实现中，业务成果优先。第一优先级是交付所需功能，其次是长期架构规划，最后是保持模块风格简洁高效。
- 严禁将任何新代码存放在高层级模块中（例如仓库根目录或其他高层级模块目录）。必须根据实际用途，将其放置在叶子模块目录中。
- `docs/architecture/repository-structure.md` 是仓库架构文件。每次修改代码前，都必须审查该文件，以确保变更符合仓库架构。修改完成后，立即更新该文件，使其与仓库保持一致。

向用户解释代码时，始终从业务角度进行说明。即使用户是开发者，也要将其视为只希望了解代码能为业务做什么、代码有哪些优势与劣势的管理负责人。

执行任何代码变更之前，必须先与用户对齐方案。只有在用户确认方案可行之后，才能开始工作。

删除文件或回滚之前，必须先在 `.agents/cache/task_name/` 中创建备份。

正向提示（标准操作，强烈鼓励的行为）：

- 编写前端代码后，自行检查 lint，并运行 `npm run dev` 检查是否存在错误。如果有错误，持续修复，直到不再出现错误信息。
- 将每个开发周期的开发日志存放在 `docs/dev_logs` 中，详细说明修改了哪些文件以及完成了什么工作。每次修改后都要更新 `dev_logs`。开发日志文档最好具备类似数据库的属性，以便进行快照回滚。存储格式应以开发日期作为文件夹名称，文件夹内的文件名表示开发内容。每个文件必须展示具体变更、修改的文件以及精确到秒的修改时间。
- 自动更新 `repository-structure.md`。
- 能够为用户自动化完成的工作都应自动完成，而不是要求用户手动操作。（如需必要信息，应主动询问。）
- 由于你的知识很可能已经过时，在安装 SDK 或 Python 软件包服务时，请在线获取最新版本并默认安装，不要使用过时的版本号。
- 对于一些固定数据（文档的大段文字、代码函数）的迁移，请尽可能不要自行生成，而是使用 Bash，或者在 `.agent/cache/task_name/` 中使用临时 Python 代码进行迁移。之后如需微调，再进行编辑。

负向提示（严格禁止的行为）：

- 编写代码后不进行任何检查或自主测试，从而导致大量错误和缺陷。
- 开发完成后不在 `dev_logs` 中记录日志，导致开发历史丢失，并为后续维护带来困难。
- 开发新功能后不更新 `repository-structure.md` 文档。
- 因为懒惰而要求用户手动完成本可通过命令行或脚本自行完成的任务（反例：“等你（用户）完成 XXX 后，我（LLM）就可以做 YYY”）。严禁这种行为！如果确实无法独立完成，必须说明：在获得 XXX 信息后，才能继续进行 YYY。
- 安装过时的 SDK 或软件包版本，例如 mathlib 4.26、PyTorch 2.7 等。最新版本早已超过这些旧版本，使用它们会给用户带来版本问题。
